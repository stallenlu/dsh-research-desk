## 0. 一句话目标

把 dsh-agent-teams 的**软件交付门禁语义**，翻译成科灵台的**科研流程语义**；再把翻译结果以**人话**写进科灵自有的 `state.json`，让既有 collab 四区**不新增字段、不认识 AgentTeams 原始结构**就能渲染。

一句话判据（同上文档:27）：研究者仍能一眼看到**研究走到哪、科灵在推进什么、哪里要自己拍板**。

### 1.2 AgentTeams 侧（语义来源）

一手文档：`raw.githubusercontent.com/NanmiCoder/dsh-agent-teams/main/docs/{usage.md,quality-gates.md}`。

- 团队真相源 `<workspace>/.agent-teams/<teamId>/team.json`（磁盘），任务状态机 `pending→claimed→in_progress→completed|failed|cancelled`；单调 `attempt` + 唯一 `attemptId`，迟到写入被拒。
- 质量 kind：`requirements / implementation / verification / review / repair / integration`（旧任务 `work` 兼容）。
- 结构化合同：`objective / acceptance[] / inScope[] / outOfScope[] / verify[] / deliverables[] / nonGoals[] / changedPaths[] / verdict(pass|needs_revision|reject) / findings[{id,severity,problem,requiredFix,resolved}] / acceptanceResults[] / commandsRun[] / round / reviewedTaskId / sourceTaskId / sourceFindingIds[] / coverageOf[]`。
- `review/requirements` 仅 `verdict=pass` 才可 completed；`needs_revision/reject` 必 failed 且 ≥1 finding；自动建 `repair-round-N+1` + `review-N+1`，不依赖 failed review。
- 范围控制是**完成时对照 changedPaths 审计**，不是 host 写入拦截；`toolPolicies` 是全局工具可见性/调用限制，**不是 OS 沙箱**（quality-gates.md §2.2/§3.1/§6.2）。
- `agent_teams_status` 返回 kind/round/verdict、coverage matrix、escalated、halt/resume；halted ≠ escalated，resume 需非空 reason。
- 已知限制：事件驱动非常驻轮询；一个队长同时一个团队；成员有完整工具集；文件级持久化不保证多进程一致；面板读磁盘真相与会话日志独立。

### 1.3 归属裁决（冻结，不在此重开）

科灵台自有 `state.json` 是用户可见进度的唯一真相源；AgentTeams 只是**执行引擎**。桥接层只读 AgentTeams 的白名单状态投影，**绝不**把 `.agent-teams/team.json` 提升为第二真相源，也不把 findings 矩阵整包塞进客户端。

## 2. 总体架构与数据流

沿用 docs/按需借用生态能力-完整实现方案.md:105-129 的六步范式，不造 pre-execute hook、不建通用工具面板：

```text
场景触发（collab_plan / collab_run / 用户点「让科灵出方案」）
  → agent 侧公共接口发现（ctx.get('tools')，取 agent_teams_status 等）
  → 副作用先在决策区拍板（ensureRiskApproval，装包/改工作区/发包）
  → AgentTeams 执行（队长 + 成员，软门禁完成时审计）
  → 桥接层白名单回流：team-bridge.translate() → store.mutate(collab)
  → libraryView 投影 → collab 四区只渲染人话
  → 工具不可用时如实提示，不伪造团队步骤
```

新增服务端模块：`lib/team-bridge.mjs`（纯函数 + 一个写入编排函数）。**客户端零新增字段**：四区继续吃 `COLLAB_FIELDS` 里已有的 steps / decisions / evaluation / goal / status。

## 3. 科研语义映射表（第 2 件事）

AgentTeams 是「把代码交付做对」的语义；科灵台是「把研究做对」的语义。映射不是改名，而是**保留门禁强度、换掉科研语境**：

| AgentTeams kind / 字段 | 科研阶段（上屏人话） | 落点字段 | 人话示例 |
|---|---|---|---|
| `requirements` + `requirements-challenger`，verdict=pass | 选题分析 | `steps[].phase` / `decision` | 「选题分析：已把研究问题与验收口径定下来」 |
| `implementation`，acceptance/inScope/verify | 分析实验 | `steps[].phase` / `reason` | 「分析实验：按方案跑完分析，改动与验证都留了证据」 |
| `verification`，commandsRun/acceptanceResults | 证据链复算 | `steps[].phase` / `refs` | 「证据链复算：结果与图表已复算，可重现」；ref 串到实验 runId |
| `review`（correctness/security/scope），verdict | 引文方法审查 | `steps[].phase` / `decision` | 「引文与方法审查：口径与引用已核过一遍」 |
| `repair`，sourceFindingIds | 补做返工 | `steps[].phase` / `decision` | 「按审查意见补做：3 处已补，1 处还在做」 |
| `integration`，deliverables | 成稿三步 | `steps[].phase` / `refs` | 「成稿三步：证据汇总成草稿，已回流内容工作流」 |
| `coverageOf[]` + 已满足集合 | 研究者的要求逐条对照 | `steps[].reason` | 「你提的 5 条要求：4 条已落实，1 条还在做」 |
| `escalated=true` / 达 maxReviewRounds | 需要人拍板 | `decisions[].point`（pending:true） | 「科灵反复核过仍拿不准：是否按现方案继续？」 |
| `halted=true` | 科灵已停下 | `collab.status=waiting-human` | 「科灵停在需要你确认的地方」 |
| `attemptId` / 迟到写入 | **不上屏**，仅内部丢弃 | —— | 不出现 attempt、attemptId 字样 |
| `toolPolicies` | 能力边界文案（逐字上屏，不伪装沙箱） | 客户端固定文案 | 见 §6.1 |

映射的三条硬约束：
1. **门禁强度不得降级**：`needs_revision/reject` 仍必须 failed 且带 findings；翻译成人话后不能变成「基本通过」。
2. **软门禁不得吹成硬拦截**：范围审计只在完成时核对，文案必须说「核对发现越界会打回补做」，不能说「越界写入已被拦截」。
3. **评审不得自批**：实现者不能把自己的实现翻成 review pass；translator 只搬运 verdict，不生成 verdict。

### 4.3 写入规则（服务端）

1. `applyProgressToCollab` 只写 `add_collab_step` / `decide_collab` / `update_collab(evaluation)` 三类既有 op，且**一次 mutate 内合并**，不嵌套。
2. 译出的 `decisions[].point` 一律 `pending:true, by:''`；**桥接层永不写 pending:false 或 by:'human'**——解除待决只能走 `collabDecisionAnswer`（lib/host.mjs:2293-2300：「只有人工拍板才能解除待决」）。
3. 译出的 `evaluation.verdict` 是人话枚举（通过/需返工/不通过/待确认），`verdictSource` 等内部字段留在服务端，不进客户端投影。
4. `evidenceRefs` 只收 `library.experiments` 里存在的 runId/id，收不到的不编造 ref（对应 lib/client.js:2700 的按 runId||id 查找）。
5. 阶段重复轮次（round≥2）以新 step 追加，不覆盖旧 step，保证时间线可追溯（lib/desk.mjs:827-837 steps.slice(-200)）。

### 4.4 严禁上屏的原始数据清单

`attemptId / attempt / findings[].id / severity 枚举 / inScope / outOfScope / changedPaths / commandsRun / coverage 矩阵对象 / toolPolicies / stateDir / memberProvider / halted 原值 / verdictSource`。这些只作为服务端计算输入；客户端文本不得出现其字段名或原始值。

## 6. 风险、边界与降级

### 6.1 软门禁不是硬沙箱（逐字上屏，按 kelin-ui 1.3）

沿用 CAPABILITY_BOUNDARY_WORDS（lib/client.js:2530）与 RISK_GATE_TEXT（:2527）：
- 「装包、改工作区、对外发包等高风险动作，须在决策区拍板后才能继续。」
- 三档权限只管工具调用、管不到实验子程序；新会话按档生效；离线只拦代理层不等于断网；**无静态代码扫描，以解释器完整权限执行**；**沙箱与确认闸门仍在实现中，不能说已约束住**。
- 门禁是**完成时审计**不是写入拦截；`toolPolicies` 是工具可见性/调用限制，**不是 OS 沙箱**。译文中禁止出现「已拦截」「已隔离」「硬约束」字样。

### 6.2 副作用拍板不变

所有装包/发包/改工作区动作仍走 `ensureRiskApproval`（lib/host.mjs:1114）；桥接层只读状态、不代办拍板。系统提示原话保持（:2830）：高风险只能真人拍板，科灵不能用 `collab_decision_answer` 自己代答。

### 6.3 工具不可用时如实提示

按六步范式末步：`agent_teams_status` 取不到（插件未装/会话无该工具）时，不伪造 steps，写一条人话步骤：「这次没找到团队协作工具，科灵按单线程推进，进度照常记在时间线。」——禁止 headless 自证式完成宣称。

### 6.4 多真相源与并发

AgentTeams 是磁盘真相、科灵是用户可见真相；桥接层**单向** AgentTeams→科灵，不反向写 AgentTeams。多进程不一致风险由「mtime 变了就重读」（lib/store.mjs:3-4）兜底；桥接写入必须在一次 `store.mutate` 内合并，且不嵌套。
