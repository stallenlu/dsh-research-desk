## 5. Mnemon 取舍实证论证（用户原则：有利就接、不利就不接）

### 5.1 历史为什么否掉（D3 原型，先坐实）

- `docs/三件内核-关2决策冻结.md:7`：Mnemon 在科灵代码**全库 grep=0**，仅是宿主 `mnemon_*` MCP 工具，**未接进 memoryBlock/desk 写路径**；「approve 写 Mnemon 是**假闭环**（科灵自己读不回来，踩 kelin-ui 1.3）。本轮否掉接 Mnemon」。
- `docs/KeLinTai-阶段1开放项拍板记录.md:32-35`：冻结裁决①「记忆接 dsh-mnemon → **A 维持自有 state.json**」，理由「接 B 推翻用户亲裁 D3『读不回=假闭环』，P6 已按 A 落地（memory 恒 verified:false），lib 全库 mnemon_ grep=0」。
- 一句话：**历史否决的理由是技术实现缺陷「写进去读不回来」，不是"Mnemon 这个产品不好"**。所以按用户新原则，判断"接不接"的钥匙是——**这个技术缺陷在新方案下能不能真规避**。

### 5.2 正面回答 Chief 第一问：D3「读不回」在新方案下能不能真规避 —— **不能**

- "读不回"的实质：Mnemon 是**宿主 MCP 工具**，科灵自己的记忆注入走 `state.json` 的 memoryBlock/desk 路径。approve 时调宿主 `mnemon_*` 写入，但科灵**构建 system 时不从 Mnemon 读回**，写进去的内容永远不进入科灵上下文 → 闭环断裂。
- 要"真规避"必须补一条**写后读回路径**：科灵在 memoryBlock 注入时调用 Mnemon 的 recall/query 把沉淀内容读回并消费。取证结论：
  - 当前 `lib` 全库 `mnemon_` **grep=0**（冻结:7、盘点:153「Mnemon 代码层零接入，全库 grep=0」）——**没有任何读回路径**。
  - 补这条路径 = **新工具调用 + 新依赖**，直接违反冻结 `:10`「纯函数优先，**无新依赖、无新模型调用、无后台 pass**」。
  - 新方案（`docs/阶段6-两缺口根本性解决方案设计.md`）全程在科灵自有 state/action 上做、不引 dsh-mnemon（方案 :77），**没有为 Mnemon 读回留任何接口**。
- **判定：历史 D3 的否决理由在新方案下依然成立、未被消解。**「读不回」不是历史偶然，而是"宿主 MCP 写入 vs 插件自身 memoryBlock 读取"两条路径未打通的结构性事实——新方案没有、也没打算打通它。

### 5.3 正面回答 Chief 第二问：双真相源风险在新方案下能不能真规避 —— **接了就破坏刚建立的单真相模型**

- 新方案刚确立的一致性模型（`docs/科研语义映射-人话转译层-接口设计.md`）：
  - `:50`「科灵台自有 `state.json` 是用户可见进度的**唯一真相源**；AgentTeams 只是执行引擎……绝不把 `.agent-teams/team.json` 提升为第二真相源」。
  - `:180`「桥接层**单向** AgentTeams→科灵，不反向写……多进程不一致风险由『mtime 变了就重读』兜底（lib/store.mjs:3-4）；桥接写入必须在**一次 `store.mutate` 内合并，且不嵌套**」。
  - 我亲验该写入机制属实：`lib/store.mjs:131-154` mutate 用 ALS 标志 `:134-135` **禁嵌套死锁**、`:138-143` 单次 read→draft→fn→persist 合并、`:151-153` queue 串行。这是新方案对抗多进程/迟到写入的核心护栏。
- 接 Mnemon = 引入**第二个可写记忆真相源**（state.json 画像 + Mnemon 长期记忆）。两边都能被写、都可能过时，上面这套"单真相 + 单向桥接 + 单次 mutate + mtime 重读"模型**只 protected state.json 一个源**，对第二个源无能为力 → 双真相源风险**实打实增加，不是规避**。
