## 1. 第一类 · 科研全流程助手

### 1.1 Elicit — 系统综述全流程
- 官方出处：https://elicit.com/ ；综述方案页 https://elicit.com/solutions/systematic-review
- 机制事实（官方页逐字）：把系统综述拆成 refine protocol → screen → extract → report 全流程；"Elicit autosuggests screening criteria and recommendations. You can agree, edit, or add your own"；每条决策 PRISMA-auditable（排除理由／逐标准打分／支撑引文）；FAQ 有 "Can I update my review as new papers are published?"
- 缺口一：**适配**——"人在前设标准框架内、系统主动批量推进事务（自动筛选/抽取/新论文更新综述）"，可借来补基线:45 每步等确认的短板。**不适配**——这是任务内自动化，不是 C1/C2"共同规划＋决策点商量＋科灵带队"的关系层主动；且是独立 SaaS 流程、非可嵌引擎，只能借做法不能引能力。
- 缺口二：**适配弱**——autosuggest 会随 agree/edit/add 微调。**不适配**——无跨会话长期画像沉淀，不能拿来论证"越用越懂你"。

### 1.2 ResearchRabbit — 文献发现推荐（Chief 点名，架构已亲验官方原文）
- 官方出处：https://www.researchrabbit.ai/
- 机制事实（架构 2026-11-23 web_fetch 官网原文亲验逐字）："The more you explore, the more your ideas grow...and the better ResearchRabbit becomes."；"With every search, ResearchRabbit learns, delivering smarter, more relevant recommendations."；另有用户证言 "As you select new ones from these articles, the algorithm learns your interests better"。
- 缺口二：**适配强（机制层）**——"用户每次探索行为都喂给推荐、配合方式持续调整"是"越用越懂你"最直接的成熟范式，可借科灵"从协作行为中学，而非静态记住你说了什么"（基线:53 名不副实点）。**不适配**——它学的是内容相关性排序，不是"学会如何与你协作"（风格／决策偏好／节奏）；只覆盖文献发现一段。
- 缺口一：**适配弱**——官网明打 "Follow your curiosity"，用户驱动探索，非助手主动带队。

## 2. 第二类 · 个人知识成长与记忆系统

### 2.1 Anki / FSRS — 间隔重复算法
- 官方出处：https://docs.ankiweb.net/faqs/what-spaced-repetition-algorithm
- 机制事实（官方文档逐字）：FSRS "learn your memory patterns and schedule reviews more efficiently than SM-2"；三变量 Retrievability／Stability／Difficulty 合成"memory state"，每张卡有独立 DSR；"FSRS analyzes the user's review history and uses machine learning to find parameters that provide the best fit"；"users should not tweak the parameters manually… choose an appropriate value of desired retention"。
- 缺口二：**适配强（机制层）**——"从真实行为数据学出个性化参数、每个对象有独立状态"正对位静态三数组（基线:53），是"从协作里学会怎么配合"的可借鉴工程内核。**不适配**——它学的是记忆保持率最优复习时机，非协作风格／科研习惯；且"不该手调参数"的黑箱自动调参与 C2"决策点来回商量"的透明气质相冲。
- 缺口一：**适配**——主动推送"该复习了"，系统主动发起而非等人查。**不适配**——单一复习队列，非全流程。

### 2.2 Readwise — 高亮重现与主动回忆
- 官方出处：https://readwise.io/ ；官方博 https://blog.readwise.io/hack-your-brain-with-spaced-repetition-and-active-recall/
- 机制事实（官方逐字）："uses Spaced Repetition to resurface your best highlights at the right times"；Import → Review（daily email）→ Remember；Mastery = 主动回忆（cloze/Q&A）＋间隔重复；Daily Readwise 一半随机重现未处理摘录、一半按算法排 Mastery 卡；可 "tune 权重…over and over as your interests change"；指数衰减算法＋专有 tuning。
- 缺口一：**适配强**——"每日主动把你过去的沉淀在合适时机重新送到面前"，是"助手主动把历史沉淀在恰当时机推回来"的最贴切范式，同时补 N4 完整历史记忆与"主动"。**不适配**——推的是静态摘录，不结合当前任务语境判断"此刻你需要哪条"。
- 缺口二：**适配**——tuning 权重随兴趣反复调，用户可参与个性化。**不适配**——学的是"哪条让你记住"，非协作方式。

### 2.3 Mem.ai — 如实标注不作基准
- 官方出处：https://get.mem.ai/
- 事实：官方首页已挂 "Mem is shutting down on January 15, 2027"。**不作长期基准**（产品将关停）；仅记录为自我组织笔记类的背景参照。

## 3. 第三类 · AI 多智能体协作引擎 / 任务调度（重点：闸门密集时自动推进如何不绕过闸门）

> 后端源码现状取证（本轮未重新读写业务码）：已有每步人工 approve（`lib/host.mjs:2222-2234`）、waiting-human 硬拦（`:2219-2221`）、审批 by:'human'（`:2293`）、风险动作人工闸门 ensureRiskApproval（`:1114-1133`）、写串行＋禁嵌套（`lib/store.mjs:131-154`）、mtime 重读（`:98-117`）。薄弱处见 §4。

### 3.1 LangGraph / LangChain — Interrupts（暂停-审批-恢复教科书）
- 官方出处：https://docs.langchain.com/oss/python/langgraph/interrupts （有 .md 原文）；中间件版 https://docs.langchain.com/oss/python/langchain/human-in-the-loop
- 机制事实（官方 .md 原文逐字）：节点里 `interrupt()` 抛特殊异常 → checkpointer 存状态 → 图无限等待 → `Command(resume=...)` 用同一 thread_id 恢复；**恢复时整个节点从头重跑**（非从 interrupt 那行续）。
- 闸门共存关键规则（原文）："Side effects called before interrupt must be idempotent"；"After a long interrupt, re-read external state (price, inventory, policy) before the mutating side effect. Do not assume the pre-pause world is still valid."；"When approval lives outside the graph... treat the resume value as acknowledgement that the operator returned, not as the approval decision itself... If approval is still pending, call interrupt() again instead of submitting a new job."；多 interrupt 用每个 interrupt 的 id 映射 resume 值防错配；`response_schema` 让客户端渲染类型化审批表单并校验；禁止裸 try/except 包 interrupt。
- 缺口一：**适配（机制层，非定位层）**——"暂停即持久化＋稳定游标恢复＋长暂停后重读外部状态"可借鉴来加固我们的每步确认与 waiting-human。**不适配**——解决的是"可靠恢复"而非"科灵主动带队"，不补关系层主动。
- 缺口二：无直接成长机制，**不适配**。

### 3.2 Temporal — Durable Execution + Approval Pattern
- 官方出处：https://docs.temporal.io/durable-execution ；https://docs.temporal.io/design-patterns/approval ；https://docs.temporal.io/design-patterns/signal-with-start
- 机制事实（官方 .md 原文）：每步（Activity/Timer/Signal）记入 Event History；Worker 挂了由另一个 replay 历史重建、已完成步骤不重跑；Retry Policy 重试瞬时失败、永久失败保留状态等人介入。Approval pattern = blocking wait with timeout ＋ Signal 携带结构化审批数据（approver/decision/comments/timestamp）；多级 L1/L2/L3 逐级等、任级 REJECTED 即停；超时 ESCALATED/拒绝；Query 只读进度不改状态；审计轨迹天然在 history 里。
- 原文要点："Verify approver permissions..."；"Ensure idempotency. Handle duplicate approval Signals safely... use idempotency keys"；"Design your timeout path to account for late-arriving Signals"；"Temporal processes events in a deterministic, single-threaded order, so a Signal and a timer cannot truly 'race.'"
- 缺口一：**适配（机制层）**——结构化审批数据＋幂等键＋迟到审批定义＋审计轨迹，正对我方闸门恢复与防重复的薄弱处（§4）。**不适配**——是工作流引擎的持久执行范式，非科灵关系层的"带队＋商量"。
- 缺口二：无成长机制，**不适配**。

### 3.3 CrewAI — Human Feedback in Flows（Chief 点名，架构已亲验官方原文）
- 官方出处：https://docs.crewai.com/edge/en/learn/human-feedback-in-flows （架构 2026-11-23 web_fetch 官方 .md 原文亲验）
- 机制事实（原文逐字确证）：`@human_feedback` 暂停 flow，`emit=["approved","rejected","needs_revision"]` 由 LLM 把人话折叠成结果并 `@listen` 路由；`default_outcome` 安全默认；`@listen(or_("generate","needs_revision"))` 自环做"改到通过为止"；chained routers 多级。异步：`HumanFeedbackPending` + 自定义 provider（Slack/webhook），框架自动持久化（默认 SQLiteFlowPersistence），`from_pending`+`resume` 恢复，resume handler 要幂等；`human_feedback_history` 做审计。
- ★ `learn=True`（本轮 9 家里唯一把"人工闸门"与"越用越默契"直接相连，架构亲验逐字属实）：原文参数表 `learn` 默认 False；"The LLM extracts generalizable lessons from the output + feedback and stores them in memory under learn_source"；"Before next review: Past HITL lessons are recalled from memory and applied by the LLM to improve the output before the human sees it"；"the human's job shifts from 'fix everything' to 'catch what the system missed.'"。
- 缺口二：**适配强（机制层，Chief 点名）**——这是把"每次人工反馈沉淀成经验、下次预审时召回应用"做成闭环的成熟范式，正对基线:53"记住你说了什么 ≠ 从协作里学会怎么配合"。**不适配（须显式标注）**——它 `learn_source` 默认写到 memory（`'hitl'`），我方三件内核冻结:7 否掉接 Mnemon、:20-22 把学习重定义为画像沉淀；直接照搬会碰既有冻结，属产品方向，留阶段7回用户裁决，工程侧不内部消化。
- 缺口一：**适配**——自环"改到通过为止"＋异步暂停/恢复，可借来做科灵带队时的推进节拍。**不适配**——仍是任务级审批流，不是全流程关系层主动。

### 3.4 AutoGen — Human-in-the-loop
- 官方出处：https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/human-in-the-loop.html
- 机制事实（官方页全文，验收非施工方 HTTP 200 逐字核属实）：`UserProxyAgent("user_proxy", input_func=input)` 把人当 agent 放进群聊收人工输入，`TextMentionTermination("APPROVE")` 作终止闸门（官方输出确有 "Text 'APPROVE' mentioned"）；`Handoff(target="user")` + `HandoffTermination` 把控制权转给人；`max_turns=1` 分段收集反馈。官方另明确警告阻塞式 UserProxyAgent 会 "put the team in an unstable state that cannot be saved or resumed"——反强化其"闸门语义弱、不可恢复"的判定，非反证。
- 缺口一：**适配弱**——把人当 agent 的群聊范式可启发"决策点商量"。**不适配**——闸门语义弱于 Temporal/LangGraph，且是群聊模型非全流程带队。
- 缺口二：无成长机制，**不适配**。

### 3.5 Camunda — User tasks / human task orchestration
- 官方出处：https://docs.camunda.io/docs/guides/orchestrate-human-tasks/ ；https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/
- 机制事实（官方页全文，验收非施工方 HTTP 200 逐字核属实；架构首抓时 403 未全、已由验收补全）：user task 是 BPMN 一等公民，官方原文 "The process instance stops at this point and waits until the user task is completed"；radio 表单 → exclusive gateway → `meal="Chicken"/"Salad"` 分支，Tasklist claim/complete，用户填表后驱动流程按决策分支继续。
- 缺口一：**适配**——闸门=可分配、可填表、可追踪的人任务而非一个布尔 approve，对"一般用户第一眼知道干什么"友好（契合用户一贯 UI 第一眼标准）。**不适配**——BPMN 建模范式重，与我方轻量状态机气质不同。
- 缺口二：无成长机制，**不适配**。

## 4. 横切：闸门密集下"自动推进 ≠ 绕过闸门"的共性套路（对科灵最关键）

后端把 5 家去重后归纳为同一组，逐条对照我方现状：

| # | 共性套路 | 出处 | 我方现状对照 |
| --- | --- | --- | --- |
| 1 | 闸门是执行图里的显式节点/状态、有稳定 id，恢复靠 id 对齐（LangGraph interrupt id / Temporal signal / CrewAI flow_id），不是散落 if | LangGraph/Temporal/CrewAI 官方 .md | 部分具备（decisions[].id 有 id，但恢复靠 stepPoint＋人再推一步） |

| 3 | 闸门前后严格分界：闸门前副作用幂等、闸门后写操作拿到批准才执行、长暂停后重读外部真实状态不用旧快照 | LangGraph 原文 | **薄弱**：缺"闸门后重读外部状态" |
| 4 | 批准数据带身份＋理由＋时间＋结果枚举，可查询可审计，且校验批准人权限 | Temporal/CrewAI 原文 | 部分具备（by/at/choice 有，verdict 现是只读复制 hypothesis.status `lib/host.mjs:2354`，非结构化审批数据） |
| 5 | 防错过/防重复：幂等键、迟到审批有明确定义、超时/升级路径、重复审批不覆盖原决策 | Temporal/LangGraph 原文 | **薄弱**：缺幂等键防重复＋"resume≠批准"成套语义 |
| 6 | resume/恢复只代表"人回来了"不代表"批准了"；请求变了要新起流程 | LangGraph 原文 | **薄弱** |
| 7 | 安全默认：无反馈走 needs_revision／拒绝，不放行 | CrewAI `default_outcome` 原文 | 部分具备（waiting-human 硬拦，但无"安全默认结果枚举"） |

## 5. 三个交叉发现（Chief 点名，供后续方案重点参考）

1. **CrewAI `learn=True`（缺口二）**：9 家里唯一把"人工闸门"与"越用越默契"直接连起来——每次人审反馈蒸馏成 lesson 存 memory，下次预审前召回应用，让人从"改所有"转为"抓漏"。对基线:53 名不副实点有直接参考价值；但碰三件内核冻结:7/:20-22（否接 Mnemon、学习=画像沉淀），属产品方向，留阶段7用户裁决。出处已经架构亲验属实。
2. **ResearchRabbit「越用越懂你」＋ Readwise「恰当时机主动推回」（缺口一＋二）**：前者证明"每次探索行为喂给推荐"是成熟范式（对缺口二），后者证明"把历史沉淀在恰当时机主动送到面前"是"主动＋完整历史记忆"的最贴切范式（对缺口一）。两者出处均官方，ResearchRabbit 已架构亲验。
3. **没有任何一家具备科灵完整定位**：调研的 9 家都是单段工具或单目标系统，没有任何一家实现"助手与人共同规划全流程＋决策点商量＋带队"这个科灵台完整定位。按用户对能力评估的纠正，**绝不能用"这些产品功能存在/实现完整"论证科灵台定位已满足**；它们只提供可借鉴的局部机制，不构成"科灵已达标"的证据。

## 6. 净判与边界

- **净判（候选借鉴，非结论）**：两类共通可借机制——①"系统在人设框架内主动推进＋主动把历史沉淀在恰当时机推回来"（对缺口一）；②"从用户真实行为学个性化参数、每个对象独立状态、用户可参与微调/反馈蒸馏复用"（对缺口二）；③"闸门显式化＋稳定游标恢复＋幂等防重＋闸门后重读外部状态＋resume≠批准"（对我方闸门密集下的可靠推进）。均为候选，不下"引入哪个/是否引入"裁决。
- **核验层级（如实标注）**：
  - 架构亲验官方原文（2 条，Chief 点名核心交叉发现）：CrewAI `learn=True`、ResearchRabbit 官网文案——均已 web_fetch 逐字核对。
