## 0. 最高标尺：用户对「科学可行主动性」的权威定义（用户本群消息，逐字）

> 用户原话（本群消息，KeLinTai 已确认为阶段6方案最高标尺）：
> "团队可能对于科灵的理解不到位：科灵是需要科学可行的主动性的，不是一个只是按照人的意志做的被动型智能体。例如，如果它发现了研究人员没有注意的问题，应该及时提醒研究人员；如果它根据研究人员的灵感偏好分析调研，发觉了需要主动和研究人员沟通的，需要及时通知研究人员。等等"

据此，缺口一「主动」的正向定义钉死为四条（KeLinTai 归纳）：

| 标尺 | 含义 | 落到本方案的可证伪判据 |
| --- | --- | --- |
| A1 主动发起 | 发现 Researchers 没注意的问题→及时提醒；基于偏好分析调研→主动沟通通知 | 存在"无人提问、由科灵先发起"的提醒，且挂真实证据；不是等人问才答 |
| A2 有依据不臆断 | 每条提醒必须可回链到具体 state 对象，服务端判定后才发 | 每条 notice 带 `evidenceRefs[]`，空证据不生成提醒 |
| A3 有分寸不替人拍板 | 提醒是"告知+建议"，不是自动执行、不是自动 approve | 提醒只读、不改状态、不触发 action；采纳后动作仍走既有闸门 |
| A4 不自证闭环 | 不看"单测绿/静态护栏"当"主动已实现" | 真机判定项另立、用户本人签；本设计不宣称已达成 |

**反例红线（验收已备初审标尺）**：把"主动"做成①定时轮询/静态规则、②自动替人拍板——命中任一即打回，这正是"功能存在≠定位满足"的偷换。本方案在 §1.4、§3 逐条论证如何规避。

**UI 尺度声明（用户 2026-11-23 新指示）**：现有 UI 设计（五页签、五宫格、md-card/md-hero/md-ministamps 移植基线等）**不是死规定**，一切以更好的互动、更好服务科灵定位为准。本方案 §1.3/§1.4 的"复用零 CSS 基线、不新增第二套界面、不做合规控制台"是**防自证/防第一眼看不懂**的护栏，不是把现有设计当教条——若落地时证明某个提醒呈现方式更利于定位与可用性，允许在"有依据＋非施工方复核＋真机判定另立"前提下调整界面；不无据乱改，也不拿"现有设计如此"当挡箭牌。

### 1.2 定位对齐论证（为什么这是 C1/C2 的"科灵主动带队"，而非 DAG 调度硬套）

- 定位要求：N1 全流程主动协助（`README.md:26`）、C1 科灵主动带队（`README.md:54`、按需方案:93）、C2 介于助手与托管之间、决策点来回商量（按需方案:94）。出处见需求基线 §一。
- 本方案的"主动"是**关系层主动**：科灵基于真实 state 主动发现问题、主动发起商量，人始终握拍板权——正对 C1/C2。
- 不是 DAG 调度：不建"多 agent 自动跑流程"，不替人决策（A3），不把"流水线跑完"当主动（避开验收"方向不对齐"红线）。
- 与靶心协作自建（C3）一致：机会扫描是科灵自有能力，在现有 state/action 上做，不引第三方引擎。

### 1.3 怎么落地（服务端算好人话，客户端只渲染）

四级流水线，每级都有落点和护栏：

1. **触发（真实事件驱动，非空转轮询）**：挂在主状态变更 action 成功之后，而不是定时器空扫。落点候选——`chat` 返回前（`lib/host.mjs:1570-1571` 已有 `after=readState()`）、文献入库 `add`、灵感新增 `add_inspiration`、假设推进/状态变更、实验完成后。有真实输入/变更才扫描，无变更不空转（直接满足 A1 与验收反例①）。
2. **机会识别（有依据不臆断）**：服务端内部函数（建议命名 `scanOpportunities(state, route)`，**不进 ACTIONS 白名单**以控攻击面），用已有模型路由 `routeFor`（`lib/host.mjs:1011-1014`）对 state 摘要做"缺口发现"判断。每条机会候选结构：`{ kind, humanText, whyText, suggestedAction, evidenceRefs[] }`。硬规则：`evidenceRefs` 必须指向真实 id（paper/hypothesis/draft/inspiration/experiment 或对话片段），**空证据丢弃该候选**（满足 A2）。典型场景：新增文献与在跟假设矛盾→提醒"这篇结论和你假设X冲突"；实验显示假设被推翻但未复盘→提醒；某灵感长期未推进但相关工作累积→提醒。
3. **人话转译（服务端算好）**：`humanText`/`whyText`/`suggestedAction` 全部服务端生成，明确"科灵为什么提醒你、建议你做什么（建议非执行）"；遵守 `KELIN_CHAT_SYSTEM` 既有纪律 `lib/host.mjs:788`（不暴露原始数据结构）、`:792`（归属纪律）。客户端只渲染，复用零 CSS 移植基线（md-card/md-hero/md-ministamps），**不新增第二套界面、不做合规控制台**（前端第一眼红线）。
4. **分寸闸门（主动但不越权）**：提醒本身只读——不写 state、不触发任何 action、不自动 approve。用户"采纳"后若要执行动作，仍走既有闸门链：`ensureRiskApproval` 三类高风险人工闸（`lib/host.mjs:1114-1133`）、L0/L1 每步人工确认（`:2222-2234`）、人工拍板 `by==='human'`（`:2293`）。用户"忽略"记录为反馈信号（引入 §2 成长闭环）。这是 A3 的落点。

### 1.5 风险与对应缓解

| 风险 | 缓解 |
| --- | --- |
| 提醒变骚扰（过度主动） | 每用户每类提醒有节流/去重（幂等键，借鉴 Temporal 幂等键 `docs/阶段5…:71`）；忽略信号进入 §2 校准；无证据不发（A2） |
| LLM 臆断"问题" | 证据强约束 + evidenceRefs 可回链；A2 只证"指向真实 id"、证不了"判断成立"，故提醒措辞一律用"可能/要不要核对"，并附双方原文片段供人自己判断，不替人下"冲突/被推翻"结论 |
| LLM 扫描的成本/延迟/失败降级 | 扫描只在真实 state 变更后触发（非每轮常驻），复用已有 `routeFor`（`lib/host.mjs:1011-1014`）不另起模型；扫描失败则静默跳过本次、不阻断主流程、不产生误导性提醒；成本上限纳入施工设计细化（非阻断，阶段7/施工前定） |
| 借提醒偷改状态/绕闸门 | 提醒只读硬约束；采纳后动作仍过既有闸门（§1.3 第4级、§3） |
| 定时轮询嫌疑 | 纯事件驱动，无定时器/静态规则；可证伪：无 state 变更则零提醒 |

### 1.6 是否碰冻结裁决

**不碰**。全程在科灵自有 state/action 上做，不引 dsh-mnemon、不引 session-superagent、不做 AgentTeams 开关、不动 P2-3；不新增第三方引擎。属 C3"靶心协作核心自建"范畴。
