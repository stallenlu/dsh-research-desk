## §1 候选一览（四条，覆盖从激进到保守的扩展路径）

| # | 候选 | 一句话机制 | 用户视角扩展成本（新增一类能力要做什么） |
|---|---|---|---|
| A | 声明式能力卡 | 每类能力写一份"声明元数据"，统一引擎读声明完成发现→验真→调用→回流 | 新写一张卡（schema+触发语义+闸门级别+人话模板），不改引擎 |
| B | 通用 agent 式工具自发现 + 模型按状态调用 | 把宿主工具交给模型，由模型按当前状态自选调用 | 理论上宿主注册即可见，零或极少科灵侧改动 |
| C | 复用 DSH 宿主已有注册桥接机制 | 借宿主标准注册/调用协议接入能力，不自建发现封装 | 按宿主协议注册一次，科灵侧保留场景映射 |
| D | 保留现状 + 抽公共 helper（保守改良） | 只把三处复制的六步骨架抽成公共函数，场景语义仍各写 | 新增能力仍写场景语义，但省掉重复的发现/验真/调用样板 |

## §2 候选 A · 声明式能力卡（登记在册，非结论）

### 2.1 机制怎么运作
把每一类宿主能力写成一份**结构化声明**，至少含：工具名候选、参数 schema、触发语义（挂哪个科研节点/什么条件）、参数如何从 state.json 取、结果如何翻人话、副作用闸门级别（拍板/直执行/只读）、注入防御需求、工具缺失时的诚实提示文案。由一个**统一引擎**读声明，完成现状 §1 那套发现→describe 验真→execute→按 callId 回流→缺失回落的通用管道；场景语义不丢，而是从"散落在各 service 的代码"变成"声明里显式字段"。

### 2.2 一手出处
- **本机现成的声明式范式**：`lib/mcp.mjs:31` `MCP_TOOLS` 数组——每个工具就是一个声明对象：`name`（`:33`）、`description`（`:34`）、`inputSchema`（`:35`，JSON Schema draft-07）、`additionalProperties:false`（`:47`，注释 `:29` 明写"参数拼错时立刻被拒而非静默忽略"）。这是"能力用元数据声明、由统一协议层消费"的现成一手样例，且 `:570`/`:583` 由 `tools/list` 统一暴露。
- **官方产品的声明式闸门范例**（阶段5已逐字核）：CrewAI `@human_feedback` + `emit=["approved","rejected","needs_revision"]` + `default_outcome` 安全默认（`https://docs.crewai.com/edge/en/learn/human-feedback-in-flows`，阶段5 §3.3/:78）；Camunda 把 user task 做成 BPMN 一等公民、radio 表单→exclusive gateway 分支（阶段5 §3.5/:90）。两者都是"闸门/路由用声明表达、引擎执行"的成熟形态。

### 2.3 与科灵定位的适配性
- **契合**：声明里显式写闸门级别、人话模板、注入需求，正好把阶段1坐实的"散落各处、无统一策略层"的三个闸门（拍板/白名单/注入）收成一处显式声明；场景化触发写在声明里，天然守住"不摊通用面板、场景化借用"。扩展时新写一张卡即可，用户视角扩展成本明显下降。
- **不契合 / 风险**：L3 拍板（一次性令牌、`consumed` 回写）、L4 注入防御（登录壳过滤、不可信标记）这类**强场景语义很难完全元数据化**，若强行塞进扁平 schema，容易退化成"配置驱动的第二套 DSL"，反而比现在的代码更难维护；声明式引擎本身是一次架构级引入，与"必要简单高效、不重复造车"需权衡。是否值得，属后续同尺度评估，本轮不定。

## §3 候选 B · 通用 agent 式工具自发现 + 模型按状态调用（登记在册，含红线警示）

### 3.1 机制怎么运作
不在代码里为每类能力写死触发入口，而是把宿主已装配的工具（`ctx.get('tools')` 暴露的全部）交给模型，由模型根据当前 `state.json` 与上下文自主判断调用哪个、传什么参数。新增一类能力 = 宿主注册该工具即可，科灵侧理论上零改动。

### 3.2 一手出处
- **本机现成的自发现底座**：`lib/host.mjs:52`（`ctx.get('tools')`）、`:55`（`selectExecutor`）、`:58`（`executable`）、`lib/search.mjs:18/21/23`（同款三件套）——这三处已经是"发现宿主有什么工具"的探针；调用协议 `tools.execute({calls:[{type:'tool-call',id,name,arguments}]})` 见 `host.mjs:1334`/`:1376`、`search.mjs:383`/`:430`。也就是说"让模型自己发现并调用工具"的底层原语在本机已经具备。
- **官方产品的行为驱动范式**（阶段5已核）：ResearchRabbit "With every search, ResearchRabbit learns…"、AutoGen 把人与工具都当 agent 放进群聊、由终止/转交信号驱动（阶段5 §1.2/:31、§3.4/:84）。

### 3.3 与科灵定位的适配性
- **契合**：最接近"每加一类能力改一轮代码"的根治——工具在宿主注册即可被看到，用户视角扩展成本趋近于零；模型按状态选工具也契合"科学家从事务中解放"的方向。
- **不契合 / 重大风险（本候选的红线警示）**：
  1. **与定位直接冲突**：让模型自由选工具 ≈ 给用户摊一个"通用工具面板"，正是用户明确否掉的形态；科灵要的是"场景化借用——走到科研节点才触发"，不是"模型看到一堆工具自己挑"。
  2. **踩安全红线**：模型自主调用会把拍板闸门、白名单回流、注入防御、失败如实提示**下放给模型判断**——这正是 group_goal 明令的红线（安全策略必须留统一策略层、绝不下放）。现阶段本候选**不可直接采纳**，除非能证明模型调用前必经统一的策略层闸门（那是后端到技术可行性阶段要判的，本轮只标风险，不预判可行）。
  - 收窄可能性（留后评估，非结论）：也许只对"只读、无副作用"的能力放开自发现（如 web_fetch），有副作用的能力仍走显式声明——但这已接近候选 A/C 的混合，不在此认定。

## §4 候选 C · 复用 DSH 宿主已有注册桥接机制（登记在册，出处部分待后端核）

### 4.1 机制怎么运作
不自建 `ctx.get('tools')` 发现封装，而是让科灵台通过**宿主已有的标准注册/调用协议**接入能力：科灵台本身已经是一个 MCP server（`lib/mcp.mjs`），对外暴露 `initialize`/`tools/list`/`tools/call`（`:22`/`:570`）;反过来，宿主侧亦有 MCP 连接器体系（本会话工具集可见 `mcp_connector_catalog`/`mcp_connector_status`/`mcp_connector_tools_list` 等宿主原生工具，是"宿主已有桥接机制存在"的证据）。候选设想：能力通过宿主标准协议注册一次，科灵侧只保留"场景映射"（何时用、参数从 state 取、翻人话）。

### 4.2 一手出处
- **本机实证**：`lib/mcp.mjs:1-9`（文件头明写"宿主外的 MCP server 暴露，让任何 MCP 客户端直接用科研工作台"）、`:22`（`PROTOCOL_VERSION='2024-11-05'`）、`:31`（`MCP_TOOLS` 清单）、`:570`（`tools/list` 返回清单）、`:583`（导出 handleLine + tools）——证明"声明工具清单 + 标准协议分发"这条桥在本机已实现并可运行。
- **宿主侧机制的证据边界**：本会话工具集里有宿主原生 `mcp_connector_*` 系列，可证"宿主具备连接器/注册机制"；但其配置格式、权限语义、是否可被场景化消费——**本轮未读宿主官方文档（app.asar 受保护）、未逐字亲验 API，标"待后端核"**，不凭工具名推断能力。

### 4.3 必须澄清的一处误认（沿用阶段1）
`lib/toolRegistry.mjs` 名字像"工具注册表·能力声明"，但阶段1已逐字坐实它全管 `python/node` 运行时与包漂移检测（`RUNTIMES` `:16`、`buildRegistry` `:61`、`validateCapability` `:117`、`validateRegistry` `:210`），全库唯一调用点 `host.mjs:2319`（experiment_design 展示），`ctx.get('tools')`/`execute` 零命中。**它不是宿主工具桥接机制，不能拿来当候选 C 的出处。**

### 4.4 与科灵定位的适配性
- **契合**：借生态不重复造车——用宿主标准协议而非自建发现封装，天然带注册/权限体系，方向对；科灵台已有 MCP server 基础（`lib/mcp.mjs`），不是从零起步。
- **不契合 / 待证**：宿主 MCP 连接器面向"通用工具挂载"，与"场景化借用、不摊面板"之间仍隔着一层科灵侧场景映射，这层该多厚、会不会又把扩展成本推回去，需后端核宿主 API 后才清楚；宿主桥接也不替我们决定闸门级别/注入防御，策略层仍需自建或复用。出处部分待后端补证，本轮不认定其可行性。

## §5 候选 D · 保留现状 + 抽公共 helper（保守改良，登记在册）

### 5.1 机制怎么运作
不动整体架构，只把阶段1坐实"三处逐字同构"的六步管道（发现自检→selectExecutor→describe 验真→executable 查定义→execute→按 callId 取结果）抽成一个公共 helper；每类能力的场景语义（触发时机、参数从 state 取、人话翻译、副作用闸门、注入防御、缺失提示）仍各写各的，只复用通用管道。

### 5.2 一手出处
阶段1逐字取证的三处同构代码：`lib/host.mjs:51-64`（`draftImageTool`）、`:70-85`（`scihubTool`）、`lib/search.mjs:17-31`（`webFetchTool`）——发现/验真骨架逐行同构；调用按 callId 匹配 `host.mjs:1336`/`:1378`、`search.mjs:384`。这些是"可抽公共层"的直接证据。

### 5.3 与科灵定位的适配性
- **契合**：最小改动、零产品方向风险、不碰任何冻结裁决（dsh-mnemon/session-superagent/AgentTeams 开关/P2-3）；场景化触发与闸门完全保留原样，不摊面板；守"必要简单"。扩展成本下降来自"省掉重复的发现/验真/调用样板"。
- **不契合**：只减重复模板那部分（阶段1量化的约 9 项），场景语义写死的部分（约 4 项：触发/取参/人话/拍板+注入）不变，扩展成本下降有限——从"新增一类改 8-13 处"看，预计只能减到约 6-9 处（静态估算，待后端/测试量化）。不根治"每加一类改一轮"，只是把每轮的样板行数变短。

## §6 用户视角扩展成本覆盖（四候选同维度对照，只列事实不下结论）

| 维度 | A 声明式能力卡 | B agent 自发现 | C 宿主桥接 | D 抽公共 helper |
|---|---|---|---|---|
| 新增能力的科灵侧动作 | 写一张声明卡 | 宿主注册即可（理论） | 宿主注册+场景映射 | 写场景语义（省样板） |
| 通用管道是否重复 | 否（引擎统一） | 否（模型自发现） | 否（宿主协议） | 否（public helper） |
| 场景语义（触发/取参/人话/闸门/注入）由谁承载 | 声明字段显式 | 模型判断（踩红线） | 科灵侧场景映射 | 各 service 自写 |
| 闸门/白名单/注入是否留在统一策略层 | 可（声明显式，待技术核） | **有下放风险（红线）** | 部分（宿主+自建） | 是（现状不变） |
| 产品方向/冻结风险 | 中是架构级引入 | 高与定位冲突 | 中依赖宿主 API | 低不动架构 |
| 出处充分性 | 本机+官方充分 | 本机+官方充分 | 本机部分，宿主 API 待核 | 本机充分 |

> 本表只按同一维度摆事实，不构成"哪个更好"的裁决；阶段3再做同尺度评估收敛。
