## §0 三把尺子的出处（先立标尺，不凭印象）

三把尺子都来自项目权威原文与已验收的 UI 章程，逐字可追：

1. **尺子①守不摊面板 / 仍场景化**：README.md:41 逐字「它**不是**：通用文献管理器…它只做"研究流程的状态与证据链"」；`docs/按需借用生态能力-完整实现方案.md:66` 逐字「**不建通用工具面板**（罗列全部工具+手动填参数的通用面板已被否决回退）」；架构文档 §3.3 亦记 B 候选此风险。
2. **尺子②一般用户第一眼**：kelin-ui 章程 R7「非施工人不提示不看文档，5±0s 看截图，独立写出『这是什么』+『下一步点哪』」；R4「禁高级/初级/[object Object]/裸 id/内部枚举，grep 命中数=0」；README.md:49「工具应当拿来就能用，不该逼研究者先学会配置」。
3. **尺子③科研人扩展体验**：用户本次问题原话——每加一类能力就要改一轮代码（ACTIONS 动作+取工具封装+测试），对用户视角扩展极不友好；group_goal「必要简单高效、借生态不重复造车」。注意区分：**不追求广度是定位（守），扩展不友好是架构问题（改）**，两者不可混。

## §1 现有 UI 的实证基线：借用是怎么做到"场景化、不摊面板"的

评候选前先钉死现状 UI 真值（当前工作树 `lib/client.js`，逐字 inspect/grep）：

- **UI 上只有五个科研页签，没有工具面板**：`lib/client.js:1850` `const NAV = [['home','灵感'],['discover','资料'],['research','选题'],['lab','虚空'],['insights','复盘']]`。五个都是科研流程节点，不存在"罗列所有宿主工具"的入口。这是"不摊通用面板"在客户端的硬证据。
- **新增一类能力在 UI 侧的做法是"场景主行动 + 人话提示"**：配图能力不是做成工具条目，而是挂在成稿场景里——`lib/client.js:1562-1590` `requestIllustration`，用户点的是主行动「让科灵配一张图」这类有底座的按钮（`:1566` prompt 由草稿算出，`:1559-1560` `runDraftImage` 走 action，`:1586` 回执人话「科灵已经配好一张图。」），闸门交服务端（`:1568` `d.gate==='waiting-human'` 时挂既有决策区，`:1558` 注释「挂进决策区由真人拍板，不另造拍板 UI」）。
- **工具可用性只作人话提示，不暴露内部实现**：`lib/client.js:2126-2128` `imageToolTip` 用「检测到订阅生图工具…」/「未检测到…请填自有接口或等工具装好」两句白话告知，落在设置项 `:3122`，不是给用户一个工具开关列表。
- 结论：现状 UI 的关键优点——**用户永远只看到"科研下一步"，看不到"工具清单"，也看不到工具名/参数/schema/闸门级别这些内部术语**。这是评 A/B 会不会倒退的基准线。

## §2 候选 A · 声明式能力卡 —— 用户视角评估

**机制**（引自架构 §2，不改措辞）：能力写成结构化声明（工具名/参数schema/触发语义/闸门级别/人话模板/注入需求/缺失文案），统一引擎读声明跑通用管道。出处 `lib/mcp.mjs:31` MCP_TOOLS、`lib/mcp.mjs:570` tools/list。

- **尺子①守不摊面板/场景化 —— 守住（前提：声明里"触发语义"仍挂科研节点）**：架构 §2.1 明写"场景化触发写在声明里，天然守住不摊面板"，与本前端基线 §1 一致。用户看到的仍应是场景主行动，不是工具卡列表。**但须设一条硬约束**：声明卡绝不能有一张"全部能力清单"的 UI 投影；`lib/client.js:1850` 五页签不得因引入卡片而多出一个"能力/工具"页签，否则直接违反 README.md:41 与方案 :66。这一条应作为 A 候选进入阶段3的前置条件写死。
- **尺子②第一眼懂 —— 取决于"人话模板"是不是服务端算好**：架构声明字段里含"人话模板"，若这条模板是**服务端渲染好的整句白话**（沿用本前端基线 `:1586`「科灵已经配好一张图。」的形态），客户端只渲染，R7/R4 都能过。风险点：若"人话模板"被理解成让客户端拿字段去拼字符串，就会重现 verdict/裸 id 那类内部术语上屏（R4 FAIL）——架构 §2.3 也承认强场景语义难元数据化。**判据**：A 的"人话字段"必须是成品白话，不是可拼的碎片；这条须在阶段3定死，否则 A 会把 R4 风险带进来。
- **尺子③科研人扩展体验 —— 本候选意图最契合用户诉求，但门槛在"卡怎么写"**：架构 §2.1 称扩展成本明显下降。从用户视角看，新增能力从"改 ACTIONS+封装+测试一轮"变成"写一张卡"，方向对；但"一张卡"要填触发语义/闸门级别/人话模板等字段，对扩展者（维护者，非终端科研用户）仍有认知负担。只要卡是声明式而非另一种 DSL（架构 §2.3 已警示"第二套 DSL"风险），对终端用户无感、对扩展者省事，是四候选里用户视角最友好的之一。
- **净判（用户视角，非裁决）**：方向契合三把尺子，但**两个前置条件必须进阶段3**：(a) 不得产生"能力清单"UI 投影、不动五页签；(b) "人话模板"必须是服务端算好的成品白话、客户端零拼字段。满足则 A 在尺子①②③上均优于现状；不满足则倒退。技术可行性（闸门/注入能否真元数据化）留后端。

## §3 候选 B · agent 式工具自发现 + 模型按状态调用 —— 用户视角评估

**机制**（引自架构 §3，不改措辞）：宿主已装配工具交模型，模型按 state.json 自主判断调用哪个。出处 `lib/host.mjs:52/55/58`、`lib/search.mjs:18/21/23`。

- **尺子①守不摊面板/场景化 —— 直接冲突，本前端明确顶这条**：架构 §3.3 已标红线，我逐字复核同意。让模型看到一堆工具自己挑，等价于把"工具选择权"摆到用户面前——即便 UI 上没有一个叫"工具面板"的容器，用户也会在对话里被反复问"要不要调用 X 工具"，这与本前端基线 §1「用户只看到科研下一步、看不到工具清单」正面冲突，违反 README.md:41、方案 :66。科灵的定位是"走到科研节点才场景化触发"，不是"模型看到工具自己挑"。**用户视角结论：B 在尺子①上不可接受**，除非按架构 §3.3 末尾的收窄（只对只读无副作用能力放开、且仍藏在场景主行动后）——那已不是纯 B，且与 A/C 混合，阶段3另行评估。
- **尺子②第一眼懂 —— 会把内部术语和决策负担推给用户**：模型自发现调用若不经过场景收敛，用户对话里会冒出工具名、参数、调用成功/失败等技术回执，直接撞 R4（禁裸 id/内部枚举）与 README.md:49「不该逼研究者先学会配置」。第一眼里"这是什么/下一步点哪"会被工具选择噪声淹没，R7 过不了。
- **尺子③科研人扩展体验 —— 表面最省（宿主注册即可见），实为把扩展成本转嫁成对用户的可解释性债**：架构 §3.3 称扩展成本趋近零，但安全闸门下放给模型的风险（架构 §3.3 第2点、group_goal 红线）意味着每次新增能力都要额外证明模型不会绕过拍板/白名单/注入——这笔成本不消失，只是从"改代码"变成"证明模型可控"，且直接威胁用户信任。对我前端而言，B 是四候选里**唯一在尺子①②③上同时亮红灯**的。
- **净判（用户视角，非裁决）**：B 不守尺子①（与定位冲突）、尺子②（第一眼被工具噪声淹没）、尺子③（扩展省的是代码、欠的是可解释性与安全），用户视角**不建议作为主路径**。是否保留"只读能力收窄自发现"的变体留阶段3与后端安全判断一并评估，本文不认定。

## §4 候选 C · 复用 DSH 宿主已有注册桥接机制 —— 用户视角评估

**机制**（引自架构 §4，不改措辞）：借宿主标准注册/调用协议接入，科灵侧只留场景映射。出处 `lib/mcp.mjs:1-9/:22/:31/:570`，宿主侧 API 架构标"待后端核"。

- **尺子①守不摊面板/场景化 —— 方向对，但"场景映射"这层是守成的关键**：架构 §4.4 明确"宿主 MCP 连接器面向通用工具挂载，与场景化借用之间隔着一层科灵侧场景映射"。从用户视角，只要这层场景映射存在且把工具藏在科研节点后（同本前端基线 §1），就不摊面板；若图省事把宿主连接器清单直接透到 UI，就退化成通用面板。**判据**：C 必须保留科灵侧场景映射、不得把宿主工具清单直呈用户；这与架构 §4.4 的担忧一致，应作为 C 进入阶段3的前置条件。
- **尺子②第一眼懂 —— 取决于场景映射是否继续算好人话**：宿主协议返回的是通用工具结果（可能是结构化字段），若直接渲染会撞 R4。**必须**由科灵侧场景映射把结果翻成人话（沿用本前端基线 `:1586`/`:2126-2128`），用户才看得懂。架构已指出宿主桥接"不替我们决定闸门/注入"，同理也不替我们算人话——这层客户端/服务端人话层 C 不能省。
- **尺子③科研人扩展体验 —— 潜在最省，但出处缺口使其暂不可判**：架构 §4.2 如实标宿主 API 语义"待后端核"。用户视角能说的只是：若宿主注册真能"注册一次、科灵侧只留薄映射"，扩展体验优于现状；但宿主连接器是否面向"场景化消费"、映射层要多厚，未核之前不能下结论。本文沿用架构的"待后端核"，不越界预判。
- **净判（用户视角，非裁决）**：C 在尺子①②上**条件性守住**（前提是保留场景映射 + 人话层、不直呈工具清单），尺子③待后端核宿主 API 后才能判。归属"方向对、证据待补"，不预设可行或不可行。

## §5 候选 D · 保留现状 + 抽公共 helper —— 用户视角评估

**机制**（引自架构 §5，不改措辞）：只把三处同构六步管道抽公共 helper，场景语义仍各写。出处 `lib/host.mjs:51-64/:70-85`、`lib/search.mjs:17-31`。

- **尺子①守不摊面板/场景化 —— 完全守住**：D 不动 UI、不动触发方式、不动五页签（`lib/client.js:1850`），本前端基线 §1 原样保留。用户视角零风险。
- **尺子②第一眼懂 —— 现状即基准，无变化**：D 不碰人话文案与界面结构，R4/R7 维持现状，不引入新术语、不摊面板。用户视角零变化（既不变好也不变坏）。
- **尺子③科研人扩展体验 —— 只省样板，不根治用户所指问题**：架构 §5.3 自评"预计 8-13 处减到约 6-9 处（待量化）"。从用户视角看，用户痛点是"每加一类能力就要改一轮代码"，D 只是把每轮代码变短，没有消除"改一轮"本身。这是 D 的根本短板——**它最安全，但最不能回应用户的诉求**。
- **净判（用户视角，非裁决）**：D 在尺子①②上零风险、是稳妥底座，但在尺子③上改善有限，不能单独作为满足用户诉求的答案。可作为其他候选（A/C）落地时的"通用管道抽公共 helper"配套动作，而非独立根治方案。

## §7 必须进阶段3的用户视角硬约束（无论最终选哪条）

这些是从本前端基线 §1 与 kelin-ui 章程导出的、任何候选落地都不能破的约束，供阶段3收敛时逐条勾：

1. **五页签不变**（`lib/client.js:1850` 灵感/资料/选题/虚空/复盘），不得新增"能力/工具/通知中心"页签（README.md:41、方案:66）。
2. **不得有"全部能力清单"UI 投影**：用户永远只看到场景主行动（本前端基线 `:1562-1590`），看不到工具名/参数/schema/闸门级别。
3. **人话必须服务端算好、客户端零拼字段**：任何候选都不得让客户端拿 kind/verdict/runId/工具名拼句子，否则撞 R4（kelin-ui 章程第四节）。
4. **闸门仍走既有决策区**：有副作用的借用仍挂 `lib/client.js:1558-1590` 那套"服务端 gate waiting-human → 既有决策区拍板"，不另造拍板 UI（这也符合 group_goal「安全策略留统一策略层、不下放」）。
5. **工具不可用如实提示**：沿用 `:2126-2128` 白话提示形态，不摆假按钮、不静默失败（README.md:49、章程 1.3）。
