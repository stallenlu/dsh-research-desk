## §2 候选 A · 声明式能力卡：四维度怎么落实、落哪层

### 2.1 机制回顾（沿用架构 §2，不重复认定）

每类能力写一张声明（工具名候选、参数 schema、触发语义、取参、人话模板、闸门级别、注入需求、缺失文案），统一引擎读声明完成发现→验真→execute→按 callId 回流→缺失回落。

### 2.2 四维度逐条落点

- **闸门**：卡的 `gateLevel` 字段（拍板/直执行/只读）只作为**引擎触发判定的输入**；真正的放行判定仍调 `lib/approval.mjs:canProceed`（:30-39），不新写第二套。触发动作由引擎在调用前统一执行——把现状分散的 `ensureRiskApproval`（host.mjs:1252）、`humanApproved`（:1322）、实验拍板（:1974/:1996）收成引擎一处。落层：**判定 = approval.mjs（统一层不动）；触发 = 新引擎（收口）**。
- **白名单回流**：卡的 `resultPolicy` 字段写白名单目录/MAX_BYTES/是否文本类；引擎统一按 callId 取结果（`host.mjs:1336` / `search.mjs:431` 的范式）、统一有界读取（`host.mjs:103/253/313` 的范式）。落层：**新引擎统一执行**，现状三处同构代码归一。
- **注入防御**：卡的 `untrustedNotice` 字段（仅文本类能力填）；引擎在结果入 state 前统一前置 `WEB_UNTRUSTED_NOTICE`（search.mjs:13 现存常量可作模板）与 host.mjs:1565-1566 的 chunk 前置范式。落层：**新引擎统一前置**。
- **失败如实提示**：卡的 `unavailableText` 字段；引擎统一回落（host.mjs:47/68、search.mjs:426 现为三套文案，归一到引擎读取字段）。落层：**新引擎统一**。

### 2.3 插件自报安全红线核验

**不踩，但有一个必须写死的前提**：卡由**科灵方自己维护**（第一方策略配置），引擎把卡上的安全字段当"科灵策略层声明"消费；**绝不可把被借插件自报的注解（`readOnlyHint`/`destructiveHint` 等）直接抄进卡当安全依据**。

权威出处（本轮 HTTP200 亲抓 `https://modelcontextprotocol.io/specification/2025-06-18/server/tools`）——Tool 数据类型段逐字：

> "For trust & safety and security, clients MUST consider tool annotations to be untrusted unless they come from trusted servers."

即：注解是行为提示、不是执行边界；客户端**必须**视为不可信（除非来自可信服务器）。User Interaction Model 段逐字：

> "For trust & safety and security, there SHOULD always be a human in the loop with the ability to deny tool invocations. Applications SHOULD: Provide UI that makes clear which tools are being exposed to the AI model; Insert clear visual indicators when tools are invoked; Present confirmation prompts to the user for operations, to ensure a human is in the loop."

即闸门必须在客户端/宿主侧、有人工 deny 能力，不能靠工具自己声明。→ 候选 A 只要卡是科灵写的、安全字段经策略层校验而非照抄被借工具注解，就同时满足这两句；若哪天把卡改成"由插件自报生成"，立刻踩红线。

### 2.4 技术可行性判断

可行，但属**架构级引入**：新引擎是新增的统一策略层，现有 `approval.mjs` 可原样复用作为闸门内核，不需要推翻；风险在架构 §2.3 已列的"强场景语义难元数据化"（生图一次性令牌 `consumed` 回写 :1322、SSRF 防线 :207、注入面判定），若强行扁平化会退化成第二套 DSL。本轮只标可行性，不认定采纳。

## §3 候选 B · agent 式工具自发现：四维度怎么落实（红线重点）

### 3.1 机制回顾（沿用架构 §3）

把 `ctx.get('tools')` 暴露的全部宿主工具交给模型，由模型按 state 自选调用；新增能力=宿主注册即可。本机自发现底座确实具备：`ctx.get('tools')`（host.mjs:52）、`selectExecutor`（:55）、`executable`（:58）、`tools.execute({calls:[...]})`（:1334/:1376）、search.mjs:18/21/23 同款——这点架构已坐实，不重复。

### 3.2 四维度逐条落点——全部存在"下放给模型"的倾向

- **闸门**：模型自选工具=由模型判断是否拍板 → 把闸门判定下放给模型判断。`approval.mjs:canProceed` 若只在模型"想起来"时才调，等价于没有统一闸门；MCP 规范明文 "there SHOULD always be a human in the loop with the ability to deny tool invocations"——模型自主调用不经人工 deny 通道即违背。**这是 policy 层下放，踩红线。** 除非在模型调用前插一道引擎级强制网关（任何有副作用调用必经 `canProceed`、无批准不许 execute）——但那层一加，就不再是"纯 B（模型自发现直接调）"，而是 B+A/C 混合，须重新定义候选。
- **白名单回流**：模型直接消费工具返回结果，可能拿到任意路径；要保住"任意工具返回路径不得变文件读取接口"，必须引擎层强制 callId 白名单 + 白名单目录 + MAX_BYTES（`host.mjs:1336` / `:103/253/313` 范式），不能靠模型自觉。落层：**只能落引擎强制层，不能靠模型**。
- **注入防御**：web_fetch 返回若不前置 `WEB_UNTRUSTED_NOTICE`（search.mjs:13）就被模型直接读进上下文，是教科书式 prompt 注入；必须引擎强制前置（host.mjs:1565-1566 范式），不能靠模型判断"这是外部数据"。落层：**只能落引擎强制层**。
- **失败如实提示**：模型在工具不可用/返回错误时可能编造答案（幻觉），这是本候选最危险的失败模式——现状靠显式 `UNAVAILABLE` 常量（host.mjs:47/68）+ `UNKNOWN_TOOL` 分支如实回落，交给模型就没有确定性保证。落层：**只能落引擎强制层**。

### 3.3 红线核验结论

**打回（不可直接采纳）**：四维度全部有下放到模型判断的倾向，其中闸门维度直接违反 group_goal「安全策略必须留统一策略层、绝不下放」与 MCP 规范的人工-in-the-loop 要求。架构 §3.3 已标"本候选不可直接采纳"，本轮从技术可行性侧**独立坐实同一结论**：不是"模型可能忘了调闸门"的担忧，而是"模型自选调用"这一机制本身与"调用前必经统一闸门"在结构上互斥——除非加引擎强制网关，而那已改变候选定义。

收窄可能（留阶段3评估，非结论）：只对只读、无副作用能力（如 web_fetch）放开自发现，有副作用仍走 A/C 显式声明——本机 `fetchOriginReachability`（search.mjs:412-436）已经是"只读、不新增 approval 闸、可注入 fetcher"的现成样例，但它是**代码里写死的单一能力**，不是"模型自发现"。这已是混合方案，不在此认定。

## §4 候选 C · 复用 DSH 宿主注册桥接：四维度怎么落实 + 出处边界

### 4.1 机制回顾（沿用架构 §4）

借宿主标准注册/调用协议接入，不自建发现封装。本机可证的只是"科灵自己已是 MCP server"：`lib/mcp.mjs:31` `MCP_TOOLS` 清单、`:33-48` 声明式工具定义（JSON Schema draft-07、`additionalProperties:false`，注释 :28-29 明写"参数拼错立刻被拒而非静默忽略"）、`:570` `tools/list` 暴露。

### 4.2 出处边界（如实标注，不编造）

- **未亲验部分**：宿主侧 `mcp_connector_*` 体系的配置格式/权限语义/可否被场景化消费，本轮**未能逐字核**——DSH 官方文档在 `app.asar` 内、`ops_inspect_local_file` 返回 `PATH_RESTRICTED`（no-follow 保护），`ops_discover_tools` 查 `cordis_inspect_query` 无匹配能力。故宿主桥接的 API 语义标"待证"，不凭工具名猜。
- **可用的一手规范**：MCP tool annotations 安全定性（§2.3 已引，HTTP200 亲抓）适用于任何"借宿主协议暴露工具"的候选——这正是候选 C 的风险点所在。

### 4.3 四维度逐条落点

- **闸门**：**关键红线分歧点**。宿主 MCP 连接器会带工具注解（`readOnlyHint`/`destructiveHint`），若把"宿主已注册=可信"或"注解说只读=不用拍板"当作放行依据，直接违反 MCP 规范 "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"。落实方式只有一种：宿主协议返回的工具能力与注解**只用于发现和调用**，放行判定仍由科灵侧 `approval.mjs:canProceed`（:30-39）独立执行、人工 deny 通道仍走科灵决策区（:1252-1271）。落层：**闸门留科灵侧统一层，不因"宿主桥接"而省**——这也意味着候选 C 在闸门维度上并不比 A/D 省事。
- **白名单回流**：宿主协议返回的路径/内容仍须科灵侧按 callId 白名单 + 白名单目录 + MAX_BYTES 校验（`host.mjs:1336/:103/253/313` 范式），不能因"宿主可信"跳过。落层：**科灵侧统一层**。
- **注入防御**：宿主返回的外部文本仍须前置 `WEB_UNTRUSTED_NOTICE`（search.mjs:13）——宿主桥接不替我们判断哪段是外部不可信数据。落层：**科灵侧统一层**。
- **失败如实提示**：宿主返回错误码需科灵侧翻成人话（一般用户第一眼标准），不能裸传。落层：**科灵侧统一层**。

### 4.4 技术可行性判断

**部分可行但"省掉的红利"被安全红线抵消**：宿主桥接能省掉的是"发现封装"（`ctx.get('tools')` 三件套），但闸门/白名单/注入/失败提示四维度**一维都不能跟着省**——都得留在科灵侧统一策略层。所以候选 C 真正省下的只是架构 §1 六步里的第 1-2 步（发现/验真），且这部分红利建立在未亲验的宿主 API 语义上。出处不足（宿主 API 待核）时不宜认定可行性，须补证后再评。

## §5 候选 D · 保留现状 + 抽公共 helper：四维度怎么落实

### 5.1 机制回顾（沿用架构 §5）

只把三处逐字同构的六步管道抽成公共 helper；场景语义（触发/取参/人话/拍板/注入/缺失提示）仍各写各的。

### 5.2 四维度逐条落点

- **闸门**：**完全不动**——仍 `approval.mjs:canProceed`（:30-39）+ 各 service 触发点（host.mjs:1252/:1322/:1974/:1996）。零下放风险，现状一致性最强。落层：**维持现状**（判定统一、触发分散）。
- **白名单回流**：helper 内统一 callId 匹配（host.mjs:1336 / search.mjs:431 范式）+ MAX_BYTES（:46）+ 白名单目录有界读取（:103/253/313）——这是候选 D 的主要收益点。落层：**新公共 helper**。
- **注入防御**：helper 内对"文本类结果"统一前置 `WEB_UNTRUSTED_NOTICE`（search.mjs:13）；但"哪些能力是文本类、需不需要注入标记"本身是场景语义，helper 只能提供"调用方声明是否文本类"的入参，判定仍归各 service——所以注入维度只能**部分**收口。落层：**helper 提供机制、service 提供判定**。
- **失败如实提示**：helper 统一不可用回落文案（host.mjs:47/68、search.mjs:426 归一口径），文案内容仍可按能力定制。落层：**新公共 helper**。

### 5.3 插件自报安全红线核验

**不踩**——不引入任何新的能力发现/调用面，不接触工具注解，四维度策略全部维持现状或收进科灵自己的 helper。风险最低。

### 5.4 技术可行性判断

**可行、零架构风险、不碰冻结裁决**，但收益有限：只减少六步样板（架构 §1 量化约 9 项），场景语义写死部分（触发/取参/人话/拍板/注入判定）不变，扩展成本下降有限（架构静态估 8-13 → 6-9 处，待测试侧量化）。这是"改良"不是"根治"，本轮不认定采纳与否。

## §6 插件自报安全红线核验总表（逐候选）
