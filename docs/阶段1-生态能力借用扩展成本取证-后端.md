## 5. 改动成本量化（按层汇总，不夸大）

以「新增一类生态借用能力」为单位，把上述三处的改动归为**必改层**与**视场景而定层**：

### 5.1 每类能力必改（三处无一例外）

| 必改项 | 三处实证 | 工程量 |
| --- | --- | --- |
| ACTIONS 加动作 | 生图/scihub/抓全文各占 `:42` 一项（抓全文占 read+verify_origin 两项） | 1—2 项 |
| 工具发现封装函数 | 三处各一个（`draftImageTool`/`scihubTool`/`webFetchTool`） | 14—16 行/处，且六步骨架逐字重复 |
| service 主方法 | `draftImage :1305` / `downloadPaper :1360` / `readPaper :1558`（抓全文主流程在 search.mjs:353） | 23—55 行 |
| dispatch case | `:2651`/`:2652`/`:2614`+`:2653` | 1—2 行 |
| 参数 schema 字段 | prompt/collabId/decisionId/dois 等 | 若干字段 |
| 工具缺失诚实回落 | `:47`/`:68`/`search.mjs:396` | 1 处 |
| 测试 | 生图 ≥25 条、scihub ≥6 条、抓全文 ≥7 条 | 每类 6—25+ 条真行为断言 |

### 5.2 视场景而定（不是每类都有，但一旦有就得写死）

| 场景层 | 生图 | scihub | 抓全文 | 说明 |
| --- | --- | --- | --- | --- |
| 高风险闸门 | 有（人工拍板 + 一次性令牌，约 20 行，与配图场景耦合） | 无 | 无 | 副作用类能力才有；闸门 point 前缀、令牌消费都是场景特化 |
| 人话错误分类层 | 重（`redact`/`explain`/魔数/SSRF，约 90 行） | 薄（透传宿主 message） | 中（NOTICE + 提纯 + 壳页判定） | 宿主返回越不可读，本地人话层越重 |
| 前端场景化 UI | 重（约 40 行含审批交互） | 无专门入口 | 轻（1 行 read） | 取决于该能力是否需要在界面暴露触发点 |
| 外部数据注入防御 | 无（图片路径） | 无（本地 PDF） | 有（`WEB_UNTRUSTED_NOTICE`） | 抓外部网页数据才有 |

### 5.3 结构性事实

1. 六步发现/探测/调用骨架在三处**重复实现**，没有单一公共层——这是「每加一类就复制一遍样板」的直接来源。
2. 每类的**场景语义**（触发时机、参数从 state 怎么算、人话怎么翻、要不要拍板、注入怎么防、缺失怎么提示）都写死在各自 service 方法里，且差异极大（生图 55 行含闸门，scihub 30 行纯透传，抓全文跨两个文件）。
3. 闸门/白名单/注入防御/失败提示**目前分散在各能力内部**，没有统一的策略层统一施加（生图自己验 `humanApproved`、抓全文自己加 NOTICE、scihub 自己判 isError）。
