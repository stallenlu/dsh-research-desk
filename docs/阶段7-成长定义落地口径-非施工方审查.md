### 7.1 现状事实（本轮亲验）

- **lib 全库 `mnemon` 零命中**：`ops_grep` lib/ `mnemon|Mnemon|dsh-mnemon|memoryBlock` → 仅 4 条，全是自有 `memoryBlock()` 函数（`lib/host.mjs:893` 定义，`:1520`/`:2477`/`:2740` 调用），无一处 mnemon_* 写/读路径。坐实冻结:7「Mnemon 仅是宿主 MCP 工具、未接进 memoryBlock/desk 写路径」至今属实。
- **唯一真相源是自有 state.json**：`lib/store.mjs:1-4` 逐字——"State lives in $DSH_HOME/research-desk/state.json so the desktop app and the web app share one copy… every write re-reads the file when its mtime moved"（单副本 + mtime 重读防双进程）。记忆走自有画像通道（`[[KELIN_PROFILE]]`，host.mjs:992-1003）。
- 既有裁决在案：冻结:7「本轮否掉接 Mnemon」；拍板记录:32 ①=「A 维持自有 state.json」（P6 已落地、memory 恒 verified:false）；剩余目标清单:132、盘点:128 同口径。

### 7.2 正面回答 Chief 的两个必答题

**问1：历史 D3「不接 Mnemon 读不回=假闭环」在新方案下能不能真规避？**

- **接的风险不可规避**：假闭环的成因是"写进 Mnemon 但科灵自己读不回"（冻结:7、拍板:32）。新方案 §1/§2 全部落在自有 state.json，**不依赖 Mnemon**——所以在"不接"前提下假闭环风险=0，根本不存在要规避的问题。若"接"且只写不读，必然重现 D3 假闭环；要规避须同时接读路径并真机验证读回属实（推翻冻结、且违反"禁自证闭环"，须用户真机签）。
- **结论**：D3 不是"新方案下能否规避"的技术题，而是"接了就重新引入、不接就没有"的方向题。

**问2：双真相源风险在新方案下能不能真规避？**

- 接 Mnemon 必然带来"记忆存哪儿"分叉：state.json 是唯一真相源（store.mjs:1-4、接口设计稿:50「绝不把 .agent-teams/team.json 提升为第二真相源」同精神）。若 state.json 与 Mnemon 双写→双真相源 + 一致性难题；若只写 state.json、Mnemon 作派生副本→派生副本必然陈旧、读它等于读旧数据；若只写 Mnemon→科灵读不回（回到 D3）。
- **结论**：接的情况下双真相源风险**无法干净规避**，三条路都踩一个既有红线。
